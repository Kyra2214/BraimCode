# 11 — cporter202/software-income-playbooks

## Objetivo

Embora seja a prioridade mais baixa da Fase 2, este repositório ensina uma coisa útil para o futuro: transformar descoberta de APIs em decisão prática.

## Estrutura

O projeto separa:

- APIs;
- playbooks;
- categorias;
- templates;
- resources.

Cada playbook descreve cliente, problema, produto, MVP, APIs, monetização, dificuldade, tempo, go-to-market e riscos.

## O que absorver para o Brain

### Capability → Opportunity

O catálogo do Brain pode ir além de “qual API faz isso?” e responder:

> “O que podemos construir com esse recurso?”

Isso pode ser útil para o modo de descoberta de projetos.

### Template de decisão

Um `OpportunityProfile` futuro pode conter:

```text
problem
customer
capability
resources
mvp
complexity
expected_value
risk
estimated_time
```

### Validação antes de overbuild

A regra “MVP pequeno antes de construir produto grande” pode entrar no planner.

### Stack de APIs

Uma capacidade pode exigir várias fontes. O Brain deve saber montar stacks e não apenas escolher um único provider.

## O que não absorver agora

- monetização como parte do core;
- lógica de vendas;
- preços sugeridos como verdade;
- dados afiliados;
- dependência de Apify.

Essas informações podem existir como conhecimento opcional para futuros projetos comerciais.

## Licença e fontes

O repositório deve ser tratado como fonte de ideias e catálogo. Algumas referências preservam links afiliados; portanto, o Brain precisa separar “informação” de “recomendação comercial”. Verificar licença antes de copiar conteúdo.

## Prioridade

**BAIXA agora / MÉDIA no futuro.**

## Conclusão

Esse repositório pode transformar o Brain de um simples “executor de tarefas” em um sistema que também entende **oportunidade → capacidade → MVP → validação**. Não é necessário para o primeiro cérebro funcional, mas pode se tornar poderoso depois.
